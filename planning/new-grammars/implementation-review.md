# Independent native runtime implementation review

Reviewed committed SQL Server `6660357` and DuckDB `a0be04c`, `2fab30f`, `3712170` from the isolated playground worktree. Findings below describe those revisions, not subsequent uncommitted fixes. Package owners received the findings directly. This is an implementation audit against existing contracts and the approved plan; coverage percentages alone do not establish readiness.

## Readiness

The native playground integration is qualified: actual native grammars analyze nine commerce queries per engine; both native database interfaces now drive batch and transaction workflow examples without a generic database cast. The native implementations require the safety and lifecycle follow-ups below before merge qualification. Package owners are implementing fixes; a follow-up review must identify concrete fixing commits and corresponding tests before closing findings.

Two additional validator integration findings apply to both reviewed implementations:

- Prepared metadata lookup must use `queryResultValidationSource(query)`. The core helper at `packages/core/src/result-validation.ts:151` exists because `sql.validateResult` creates a separate immutable query. Direct weak-map lookups on that wrapper lose native prepared registration and change prepared observations into unprepared ones. Verify native prepare counts and statement identity after validator attachment.
- Stream validation must retain the global row index and occur immediately before each consumed row. SQL Server's a12aa93 fix validates one-row arrays, resetting every error index to zero; DuckDB validates whole chunks, resetting indices across chunks and evaluating later rows before the consumer requests them. `docs/guides/result-validation.md:80` and90 define the behavior, and `validateQueryResultStream` already supplies it. An invalid third row across a native chunk boundary must report index2 after two valid rows have been yielded; early close must not validate unseen rows.

SQL Server engine/session attestation and DuckDB semantics-affecting settings allowlisting were already known root findings before this independent review. They remain required: a compiled value plan and a lossless driver are not sufficient proof that a different engine version, compatibility level, collation, timezone, or operator setting has the analyzed semantics.

## Batch atomicity: root-owned documentation resolution

The approved plan explicitly requests native atomic batches (`planning/new-grammars/implementation-plan.md:182`). Both implementations follow that choice. There is no atomicity guarantee in the neutral `QueryBatch`/`QueryResults` type definitions. Existing portable adapters also distinguish atomic capabilities (`docs/reference/portable-adapters.md:18`,61,147).

However, current public prose is overbroad: `docs/reference/api.md:169` says a root batch is neither atomic nor a one-round-trip protocol, `docs/guides/execution.md:189` says successful statements are not rolled back by a later failure, and `docs/guides/bulk-data.md:19` recommends wrapping a batch in a transaction when atomicity is needed. Those statements describe PG/MySQL behavior but are not universally true of approved native and portable adapters.

Resolution belongs to root: scope that prose to the applicable adapters and publish an explicit backend capability/atomicity table, or explicitly re-review the plan. This review does **not** instruct package owners to replace their approved atomic implementation with PG/MySQL semantics. Empty-batch behavior and full preflight/snapshot discipline still require independent regression coverage.

## Stream and cancellation checks requiring executable qualification

DuckDB uses a lazy async generator and shared per-connection queue; controlled operations await native settlement before releasing leases. SQL Server uses a lazy stream with a separate explicit close path that can interrupt a pending read; its ODBC request tracks late error/free tokens and duplicate result metadata. Those are substantive implementations, not buffered stream aliases.

The remaining tests must establish behavior under actual races, rather than merely assert method presence:

- Close before first read; close during metadata acquisition; concurrent next/return/close; early loop break; native next failure; native close failure; source error after valid rows; sibling-wrapper work during each stage.
- Cancellation while another operation owns the connection must not interrupt the wrong request. Pre-aborted signals and expired absolute deadlines must prevent dispatch. Cancellation or close during native prepare/run/fetch must await settlement before another operation acquires the connection.
- DuckDB's decoded chunk loop (`runtime.ts:401`) yields buffered rows without checking signal/deadline between rows. Abort while the consumer is paused, then request another buffered row: specify and test whether cancellation rejects before that row rather than silently yielding more rows after the abort.
- Native streams must retain bounded transport buffering and never claim batchSize is a byte limit or server cursor guarantee. DuckDB native chunks and ODBC pause/resume require real-adapter evidence, including cleanup after late additional result sets.
- Multi-result rejection must work for empty first results, late extra result metadata and error tokens. A stream can expose earlier rows before a later protocol error, but must ultimately reject and drain/cancel before reuse; tests must not mistake the first yielded row for complete success.

## Positive evidence and limits

The reviewed implementations do perform grammar-owned physical marker lowering rather than runtime SQL scanning. SQL Server validates native target strings and emits per-value CONVERT markers; DuckDB recursively lowers typed UNION transport through existing structural placeholders. Root value-plan metadata preserves NULL/empty binding targets. DuckDB recursively checks native result metadata against canonical planned types. Both runtimes preserve bigint/decimal exact policy, validate logical transport plans, and have explicit connection ownership. DuckDB native statement extraction rejects multiple statements. SQL Server ODBC observes duplicate metadata, truncation, errors and request completion, instead of coercing `number` back into pretend-exact decimal text.

These strengths do not close the findings above, and the review does not establish real SQL Server precision/ODBC support on every host. Root owns native R0 and packed qualification.

Playground follow-up evidence: twelve playground/commerce contract files pass with actual native `SqlServerDatabase`/`DuckDBDatabase` imports; native batch tuple and transaction return hovers contain exact results without `any` or `unknown`. Production browser qualification already checked grammar selection, native inspector shapes, real hover, completions, wrong input diagnostics and saved custom work. The updated native workflows also pass an actual production-built browser check: hovering each loadDashboard function shows exact native batch tuple-derived arrays. Native query hovers, real editor member completion, wrong input diagnostics and persisted custom edits pass again with zero browser errors. The production docs build and all twelve playground/commerce contract files pass. Global typecheck is blocked only by root test/tsconfig omitting the new SQL Server test/environment.ts helper after a12aa93.

### Additional close-path audit

SQL Server `runtime.ts:533` in6660357 (the same structure remains in a12aa93) checks for an existing lease, then awaits prepared-handle cleanup before setting `closed`, without reserving a close lease. A buffered request or sibling-wrapper operation can enter during that await; an owned connection can then close beneath it. Reserve shared ownership before the first await and reject competing dispatch until close completes. Regress a delayed prepared close followed by concurrent root/sibling calls and assert native connection close occurs only after exclusive cleanup.

DuckDB `runtime.ts:577` in3712170 does acquire the shared queue before close, but directly awaits prepared handles in a loop. One rejection skips remaining handles and leaves the wrapper open and shared state unbroken when the queue releases. Cleanup must continue best effort, quarantine uncertain native state, retire the closing wrapper, close owned resources, and preserve the first error. Regress two cached handles with the first close failing, verify the second is still closed, and verify sibling wrappers cannot dispatch afterward. Both owners received these findings separately.
