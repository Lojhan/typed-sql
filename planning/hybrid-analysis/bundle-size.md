# Bundle baseline and expected removal boundaries

Measured against committed PR revision `a1f27fc894e48021e91ce4c9a4b98929890f233d`.
The governing design is [the final architecture specification](./spec.md). Full byte counts,
entry sources, input digests and tool settings are in [bundle-measurements.json](./bundle-measurements.json).

## Direct answer

The large candidate pool for offloading belongs to the analyzer, not an ordinary tree-shaken query
tag. Generated inputs currently contribute about **1.38 MiB to PostgreSQL's minified analyzer**
and **1.19 MiB to DuckDB's**, representing 85.6% and 91.0% of those complete analyzer samples.
The other three analyzers have much smaller generated pools: 19.5–37.8 KiB.

Those are measured current contributions and upper bounds on generated bytes that could be
offloaded. They are not measured net savings after implementing a compact core, project
contracts, lazy profile loading and acquisition infrastructure.

The normal root `sql` import already retains **zero generated catalog bytes** in all five
tree-shaken samples. There is no additional megabyte-scale generated catalog to remove from
that production import. Execution factories retain small generated lexical/type helpers which
may be required for correct behavior; removing all generated code is not the objective.

## Measurement method

Twenty entrypoints cover four scenarios for each grammar:

1. Root tag: import `sql` from the grammar root and export `sql` tagged with `SELECT 1 AS value`.
2. Query tag: the same operation through the existing `/query` subpath.
3. Execution: export the grammar's driver-independent database factory from `/runtime`, together
   with the root `sql` tag. This preserves the execution factory's reachable behavior.
4. Analyzer: export the grammar's dialect factory from its root. This preserves dynamic profile
   selection and reachable parser/resolver behavior.

Use esbuild 0.28.2, ESM, Node platform, ES2022, minification, tree-shaking and no source maps.
Driver implementations are external. Built-in Node imports remain platform imports. Workspace
public export targets are mapped from their distribution paths to corresponding TypeScript
source paths, and every workspace source body is read from the named Git revision. This avoids
both pending working-tree changes and potentially stale compiled output. No catalog is stubbed,
deleted or replaced with a mock to create a smaller result.

Generated attribution is the sum of esbuild's `bytesInOutput` for exact TypeScript output paths
owned by the committed `grammar/catalog/generation.json`. The evidence records those paths and
their individual contributions. Other parser/resolver source is not misclassified as generated.

Whole outputs are also compressed with gzip level 9 and Brotli quality 11. Compressed sizes
belong to the entire bundle. The minified generated attribution cannot be applied proportionally
to compressed output: repeated catalog data compresses very differently from executable code.

These are synthetic source-entrypoint measurements, not a complete application, packed-consumer
test, npm installation-size measurement or browser-build measurement. The grammar-only analyzer
sample does not include the TypeScript compiler, database engine binary or future cache/scheduler
implementation. Report those separately when the new architecture has a working prototype.

| --- | ---: | ---: | ---: | ---: | ---: |
| PostgreSQL | 1,649.9 | 131.8 | 99.2 | 1,411.6 | 85.6% |
| MySQL | 180.6 | 43.2 | 36.6 | 37.8 | 20.9% |
| SQLite | 154.7 | 39.5 | 33.8 | 19.5 | 12.6% |
| SQL Server | 138.7 | 35.6 | 30.6 | 23.0 | 16.6% |
| DuckDB | 1,340.3 | 101.4 | 59.8 | 1,219.7 | 91.0% |

The PostgreSQL generated contribution is dominated by the native catalog projection; all six
major-version core catalogs are also retained. DuckDB retains the 1.5.6 and 2.0.0 catalogs and
their shared metadata. The other grammars' generated tables are a smaller share of their total
parser/resolver implementation.

Do not add the five rows to describe a typical application: a project may use one grammar.
Do not say the future analyzer will shrink by exactly these percentages. Some generated core
metadata remains and new orchestration has a cost. MySQL, SQLite and SQL Server could have a
larger complete analysis tool after live infrastructure is added, even while gaining coverage
and avoiding long-tail semantic maintenance.

## Current production-facing samples

Sizes are again KiB. Generated contributions are minified attribution, not compressed savings.

| Grammar | Root tag minified / gzip | Root tag generated | Execution factory minified / gzip | Execution factory generated |
| --- | ---: | ---: | ---: | ---: |
| PostgreSQL | 17.1 / 5.4 | 0 | 110.4 / 31.0 | 1.3 |
| MySQL | 17.1 / 5.4 | 0 | 89.6 / 26.7 | 0.9 |
| SQLite | 17.1 / 5.4 | 0 | 37.2 / 11.5 | 0 |
| SQL Server | 17.1 / 5.4 | 0 | 91.7 / 27.7 | 3.6 |
| DuckDB | 17.4 / 5.5 | 0 | 100.9 / 31.6 | 0.7 |

The retained execution inputs are PostgreSQL/MySQL lexical vocabulary, SQL Server native type
metadata and DuckDB aliases. They are not the large full-routine catalogs. The `/query` tag
samples also retain no generated catalogs. Tiny size differences between tag entrypoints reflect
their reachable renderer/runtime setup; they are not full-analysis catalog leakage.

An application importing analyzer factories, keeping a broad module namespace reachable, using
a different bundler configuration or disabling tree-shaking can have different results. Required
future gates include real packed ESM consumers and representative bundler/browser scenarios.
These tree-shaken results also do not measure unbundled Node ESM loading. A root module's static
analysis imports/re-exports can still resolve and evaluate heavy dependencies without bundling.
The lightweight-entrypoint requirement addresses that boundary independently of minified bytes.

## What the final architecture removes or retains

| Surface | Target |
| --- | --- |
| Production query/runtime imports | No global analysis inventories, native description clients, compiler or refresh machinery |
| Frozen contract consumer | No full routine/overload catalogs or full SQL analyzer implementation; load only matching contract closure and lightweight grammar/codec profile |
| Development offline analyzer | Compact selected core/profile; optional packs loaded explicitly |
| Native acquisition tools | Retain required introspection and descriptor interpretation behind lazy tooling entrypoints |
| Maintainer audit workspace | Retain complete inventories, source locks, raw evidence references and qualification tools |
| Generated runtime value plans | Retain the query-specific parameter/result metadata required for sound execution |
| Compact generated codecs/type identities/vocabulary | Retain when required; identify them explicitly rather than renaming an entire analysis catalog as runtime data |

Contract-first consumption prevents a subtle failure: loading the full analyzer just to
construct the configuration object, then deciding to use a cached contract. The heavy import has
already happened in that design. The final spec requires a lightweight profile and separate lazy
analyzer modules, and requires frozen consumers to work with those heavy modules absent.

## Savings that must not be conflated

- Profile isolation can exclude unused engine versions independently of the contract design.
- A bounded offline core can exclude specialized global semantic tables from the default analyzer.
- Exact project contracts can eliminate loading the analyzer entirely for frozen compilation.
- Existing bundler tree-shaking already excludes catalogs from the tag-only runtime samples.
- Retaining only used codecs/contracts controls project artifact growth, but generated metadata
  grows with query count; it is not a zero-byte replacement for the global catalogs.

The project contract format stores data rather than requiring generated SQL wrapper modules per
query. Generated declarations are compiler inputs; production receives only required value plans
and codecs. No application import migration to generated functions is required.

## Required after-measurement

Repeat the same twenty baseline scenarios and add:

- A minimal frozen consumer with all full analyzer modules and global catalogs absent.
- A project corpus with 10, 100 and 1,000 query variants; report metadata and declaration growth.
- Selected-profile versus all-profile analyzer loading, with and without optional packs.
- Native qualification tooling separately from runtime/frozen consumers.
- Packed ESM and browser builds with import-graph attribution and actual runtime decoding tests.
- Minified/gzip/Brotli sizes, installed bytes, startup/retained-memory and cold/warm analysis latency.

Only those results can establish net byte or percentage reductions for the implemented target.
The present evidence supports a large global-catalog offloading opportunity for PostgreSQL and
DuckDB, a smaller one for the other analyzers, and already successful catalog elimination from
ordinary tree-shaken query-tag imports.
